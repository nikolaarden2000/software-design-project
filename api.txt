Обновлённая логика admin-интерфейса

В системе есть роли user, admin, superuser.

admin управляет только теми локациями, которые ему назначил суперпользователь. superuser может пользоваться admin-интерфейсом как администратор, но видит все локации и все помещения. Backend уже защищает admin endpoints через роли admin и superuser, а superuser endpoints — только через superuser. Это видно по текущей регистрации маршрутов в backend.

Admin-интерфейс теперь строится не как одна общая страница, а как несколько страниц:

/admin
/admin/location/{location_id}
/admin/room/new?location_id={location_id}
/admin/room/{room_id}

Публичную страницу /room/{room_id} для admin-управления лучше не использовать. Она предназначена для обычного пользователя и работает только с опубликованными помещениями. Для админской страницы помещения нужно использовать отдельный маршрут /admin/room/{room_id} и admin API.

Страница /admin

Это стартовая страница панели управления.

На странице отображается таблица всех локаций, доступных текущему администратору. Для обычного admin это только назначенные ему локации. Для superuser — все локации.

Используется endpoint:

GET /api/admin/locations

Ответ:

{
  "data": {
    "items": [
      {
        "id": 1,
        "company_id": 1,
        "company_name": "ABC Coworking",
        "city": "Москва",
        "address": "Москва, Тверская 10",
        "lat": 55.7558,
        "lng": 37.6173,
        "timezone": "Europe/Moscow",
        "rooms_count": 3
      }
    ]
  }
}

Таблица локаций должна содержать примерно такие столбцы:

ID
Компания
Город
Адрес
Количество помещений
Часовой пояс

При клике на строку таблицы frontend открывает:

/admin/location/{location_id}

Никаких дополнительных endpoints для самой страницы /admin не нужно.

Страница /admin/location/{location_id}

Это страница управления помещениями конкретной локации.

На странице отображается название/адрес локации и таблица всех помещений этой локации. Помещения можно фильтровать по статусу:

draft
pending
published
rejected
archived

Для загрузки помещений используется уже существующий endpoint:

GET /api/admin/rooms?location_id={location_id}

С фильтром по статусу:

GET /api/admin/rooms?location_id={location_id}&status=draft
GET /api/admin/rooms?location_id={location_id}&status=pending
GET /api/admin/rooms?location_id={location_id}&status=published
GET /api/admin/rooms?location_id={location_id}&status=rejected
GET /api/admin/rooms?location_id={location_id}&status=archived

Ответ:

{
  "data": {
    "items": [
      {
        "id": 15,
        "location_id": 1,
        "title": "Переговорная на 8 человек",
        "price": 1500,
        "capacity": 8,
        "status": "draft",
        "rejection_reason": null,
        "created_at": "2026-04-28T10:00:00Z"
      }
    ]
  }
}

Таблица помещений должна содержать примерно такие столбцы:

ID
Название
Вместимость
Цена
Статус
Причина отклонения
Дата создания

При клике на помещение frontend открывает:

/admin/room/{room_id}

На странице также должна быть кнопка:

Создать помещение

При нажатии открывается страница:

/admin/room/new?location_id={location_id}

Никакой объект на backend при открытии пустой формы создавать не нужно. Помещение появляется в базе только после первого сохранения.

Страница /admin/room/new?location_id={location_id}

Это страница создания нового помещения.

На странице отображается пустая форма помещения. location_id берётся из query-параметра URL.

Форма должна содержать поля:

Название
Описание
Цена
Вместимость
Время доступности с
Время доступности до
Изображения

Минимальный payload для сохранения:

{
  "location_id": 1,
  "title": "Переговорная на 8 человек",
  "description": "Описание помещения",
  "price": 1500,
  "capacity": 8,
  "available_from": "09:00",
  "available_to": "21:00",
  "images": [
    "/images/room1.jpg"
  ]
}

Для первого сохранения используется endpoint:

POST /api/admin/rooms

Ответ:

{
  "data": {
    "id": 15,
    "location_id": 1,
    "title": "Переговорная на 8 человек",
    "price": 1500,
    "capacity": 8,
    "status": "draft",
    "rejection_reason": null,
    "created_at": "2026-04-28T10:00:00Z"
  }
}

После успешного сохранения frontend должен перейти на:

/admin/room/{created_room_id}

На странице создания нужны кнопки:

Сохранить как черновик

Кнопку «Отправить на модерацию» можно не показывать до первого сохранения, потому что пока у помещения нет room_id.

Страница /admin/room/{room_id}

Это основная страница управления конкретным помещением.

Она состоит из двух частей:

1. Форма с информацией о помещении
2. Блок бронирований или блок действий по черновику

Для загрузки формы используется endpoint:

GET /api/admin/rooms/{room_id}

Ответ:

{
  "data": {
    "id": 15,
    "location_id": 1,
    "title": "Переговорная на 8 человек",
    "description": "Описание помещения",
    "price": 1500,
    "capacity": 8,
    "available_from": "09:00",
    "available_to": "21:00",
    "images": [
      "/images/room1.jpg"
    ],
    "status": "draft",
    "rejection_reason": null
  }
}

Этот endpoint нужно немного расширить, чтобы frontend мог корректно показать архивирование. Предлагаемый дополнительный блок:

{
  "archive": {
    "can_archive_now": true,
    "has_active_or_future_bookings": false,
    "booking_disabled": false,
    "scheduled_for": null
  }
}

Итоговый ответ после расширения:

{
  "data": {
    "id": 15,
    "location_id": 1,
    "title": "Переговорная на 8 человек",
    "description": "Описание помещения",
    "price": 1500,
    "capacity": 8,
    "available_from": "09:00",
    "available_to": "21:00",
    "images": [
      "/images/room1.jpg"
    ],
    "status": "published",
    "rejection_reason": null,
    "archive": {
      "can_archive_now": false,
      "has_active_or_future_bookings": true,
      "booking_disabled": false,
      "scheduled_for": null
    }
  }
}
Поведение формы помещения

Если помещение в статусе:

draft
rejected

то форму можно редактировать.

Под формой показываются две кнопки:

Сохранить изменения
Отправить на модерацию

Кнопка «Сохранить изменения» вызывает:

PATCH /api/admin/rooms/{room_id}

Payload такой же, как при создании:

{
  "location_id": 1,
  "title": "Новое название",
  "description": "Новое описание",
  "price": 1700,
  "capacity": 10,
  "available_from": "09:00",
  "available_to": "22:00",
  "images": [
    "/images/room1.jpg"
  ]
}

Ответ:

{
  "data": {
    "id": 15,
    "status": "draft"
  }
}

После сохранения кнопка «Отправить на модерацию» становится активной.

Кнопка «Отправить на модерацию» вызывает:

POST /api/admin/rooms/{room_id}/submit

Ответ:

{
  "data": {
    "id": 15,
    "status": "pending"
  }
}

После отправки на модерацию форма становится readonly.

Если помещение в статусе:

pending
published
archived

форма должна быть readonly.

Если статус rejected, нужно показать причину отклонения:

Причина отклонения: ...
Бронирования на странице помещения

Для помещений в статусе:

published
pending
archived

можно показывать таблицу бронирований. Для draft и rejected таблицу бронирований можно не показывать, потому что такие помещения ещё не доступны пользователям для бронирования.

Для загрузки броней конкретного помещения нужно расширить существующий endpoint:

GET /api/admin/bookings

Добавить query-параметр:

room_id

Итоговый запрос:

GET /api/admin/bookings?room_id={room_id}

С фильтром по статусу:

GET /api/admin/bookings?room_id={room_id}&status=booked
GET /api/admin/bookings?room_id={room_id}&status=in_use
GET /api/admin/bookings?room_id={room_id}&status=finished
GET /api/admin/bookings?room_id={room_id}&status=canceled

Ответ:

{
  "data": {
    "items": [
      {
        "id": 101,
        "room_id": 15,
        "room_title": "Переговорная на 8 человек",
        "location_id": 1,
        "location_address": "Москва, Тверская 10",
        "user_id": 5,
        "user_email": "user@mail.com",
        "user_username": "Иван",
        "date": "2026-04-29",
        "start_time": "10:00",
        "end_time": "12:00",
        "total_price": 3000,
        "status": "booked"
      }
    ]
  }
}

Таблица бронирований должна содержать примерно такие столбцы:

ID брони
Пользователь
Email пользователя
Дата
Время начала
Время окончания
Стоимость
Статус
Действия

Сортировку по дате/времени можно сделать на frontend без отдельного API, если данных немного. Для MVP backend-сортировка не обязательна.

Кнопка отмены бронирования показывается только для статуса:

booked

Отмена вызывается без причины:

POST /api/admin/bookings/{booking_id}/cancel

Body не нужен.

Ответ:

{
  "data": {
    "id": 101,
    "status": "canceled"
  }
}
Архивирование помещения админом

Нужно добавить новый endpoint:

POST /api/admin/rooms/{room_id}/archive

Он доступен ролям:

admin
superuser

Обычный admin может архивировать только помещение из своей локации. superuser может архивировать любое помещение.

Архивирование бывает двух режимов.

Первый режим — немедленное архивирование:

{
  "mode": "immediate"
}

Backend должен разрешить его только если у помещения нет активных или будущих бронирований. То есть нет броней со статусом booked, которые ещё не завершились.

Успешный ответ:

{
  "data": {
    "id": 15,
    "status": "archived"
  }
}

Если есть активные или будущие брони:

{
  "error": {
    "code": "room_has_active_bookings",
    "message": "Нельзя архивировать помещение, пока есть действующие или будущие бронирования"
  }
}

Второй режим — отложенное архивирование:

{
  "mode": "scheduled"
}

Поведение:

1. Новые бронирования для помещения запрещаются.
2. Уже существующие будущие брони остаются действительными.
3. Backend рассчитывает дату после последней будущей брони.
4. После этой даты помещение должно стать archived.

Ответ:

{
  "data": {
    "id": 15,
    "status": "published",
    "booking_disabled": true,
    "archive_scheduled_for": "2026-05-10T00:00:00Z"
  }
}

Для MVP можно сделать без автоматического фонового процесса, если не успеваем: endpoint сохраняет archive_scheduled_for, а фактический перевод в archived можно делать при следующем обращении к backend или отдельным ручным SQL/cron позже. Но для frontend контракт лучше сразу заложить таким образом.

После отложенного архивирования frontend должен показывать предупреждение:

Помещение ожидает архивирования. Новые бронирования отключены.

И скрывать кнопку повторного архивирования.

Что меняется в API

Новые endpoints:

POST /api/admin/rooms/{room_id}/archive

Обновлённые endpoints:

GET /api/admin/bookings

Добавить поддержку query-параметра room_id.

GET /api/admin/rooms/{room_id}

Добавить блок archive.

POST /api/admin/bookings/{booking_id}/cancel

Оставить без причины отмены. Body не обязателен.

Не нужны новые endpoints для:

/admin
/admin/location/{location_id}
/admin/room/new
/admin/room/{room_id}

Это frontend routes, они работают через уже существующие API.

Что больше не нужно делать

Не нужно добавлять причину отмены бронирования админом.

Не нужно менять пользовательский /me.

Не нужно менять пользовательскую страницу истории бронирований.

Не нужно использовать публичный endpoint:

GET /api/rooms/{id}

для admin-страницы помещения. Для админа используется:

GET /api/admin/rooms/{room_id}
Краткая карта страниц и API
/admin
  GET /api/admin/locations
/admin/location/{location_id}
  GET /api/admin/rooms?location_id={location_id}
  GET /api/admin/rooms?location_id={location_id}&status={status}
/admin/room/new?location_id={location_id}
  POST /api/admin/rooms
/admin/room/{room_id}
  GET /api/admin/rooms/{room_id}
  PATCH /api/admin/rooms/{room_id}
  POST /api/admin/rooms/{room_id}/submit
  GET /api/admin/bookings?room_id={room_id}
  GET /api/admin/bookings?room_id={room_id}&status={status}
  POST /api/admin/bookings/{booking_id}/cancel
  POST /api/admin/rooms/{room_id}/archive

Итоговая логика такая: админ сначала выбирает локацию, затем управляет помещениями этой локации, а внутри конкретного помещения редактирует данные, отправляет на модерацию, смотрит брони, отменяет будущие брони и архивирует помещение. Причину отмены брони не указываем.
